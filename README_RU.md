# React: оптимизация окна транзакций

Технический конспект учебного проекта `TransactionsTable` - окно из **последних пяти транзакций**, выборочные обновления строк, инкрементальный расчёт среднего и проверка через React DevTools Profiler.

## 1. Цель и требования

Поток данных периодически добавляет, обновляет и удаляет транзакции. Интерфейс отображает не более `LIMIT = 5` последних транзакций и среднюю сумму по текущему окну.

**Целевое поведение:**

- Изменение суммы транзакций `tr_3` и `tr_4` не перерисовывает `TransactionsTable` и другие строки; обновляются только соответствующие `Row` и, если среднее изменилось, `AverageAmount`.
- Добавление `tr_6` при полном окне вытесняет самую старую транзакцию `tr_1`: таблица рендерится один раз для изменения состава строк, `tr_1` размонтируется, `tr_6` монтируется, остальные строки сохраняют свои экземпляры.
- Несколько операций, полученных одним пакетом, не должны вызывать отдельное уведомление подписчиков на каждую операцию.

Это упражнение про **границы подписок и идентичность данных**, а не про ускорение `Array.map()` как такового.

## 2. Структура компонентов

```text
TransactionsTable
├── Row (React.memo), key=tr_2
├── Row (React.memo), key=tr_3
├── Row (React.memo), key=tr_4
├── Row (React.memo), key=tr_5
├── Row (React.memo), key=tr_6
└── AverageAmount (React.memo)

TransactionsStore (вне состояния React)
├── transactions: Map<id, transaction>
├── subscribers: Map<id, Set<callback>>
├── idsSubscribers: Set<callback>
└── averageSubscribers: Set<callback>
```

`TransactionsTable` хранит **стабильный экземпляр** `TransactionsStore` в `useRef`. Store не создаётся заново при каждом рендере. Каждая строка подписана на свою транзакцию по `id`; таблица подписана только на список ID; среднее подписано отдельно.

## 3. Модель данных и операции Store

Основные поля:

| Поле | Назначение |
| --- | --- |
| `transactions = new Map()` | Текущие транзакции; порядок вставки определяет старейшую запись. |
| `subscribers = new Map()` | Подписчики отдельных транзакций по ID. |
| `idsSubscribers = new Set()` | Подписчики изменения состава окна. |
| `averageSubscribers = new Set()` | Подписчики среднего значения. |
| `idsSnapshot = []` | Стабильный снимок массива ID. |
| `sum = 0` | Сумма транзакций для расчёта среднего за O(1). |
| `isBatching`, `changedIds`, `idsChanged`, `averageChanged` | Накопление изменений внутри пакета. |

### `update(transaction)`

1. Находит предыдущую запись по `transaction.id`.
2. Обновляет `sum` **по разнице**: `sum += newAmount - oldAmount` (для новой записи `oldAmount = 0`).
3. Сохраняет новый объект в `Map`.
4. Помечает ID как изменённый и уведомляет подписчиков строки (сразу либо в конце batch).
5. При появлении нового ID обновляет снимок списка ID и уведомляет подписчиков таблицы.
6. Вызывает `notifyAverage()` при обновлении вне batch или устанавливает `averageChanged = true` внутри batch. React сам пропустит рендер, если результат `getAverage()` не изменился.

Если меняются другие поля транзакции, а не только `amount`, проверка изменений должна учитывать и их. Не следует молча пропускать обновление имени, статуса или текста из-за неизменной суммы.

### `delete(id)`

Удаляет запись, вычитает её сумму из `sum`, помечает изменение набора ID и среднего. Удаление отсутствующего ID не должно создавать ложное уведомление.

### `getAverage()`

```js
getAverage() {
    return this.transactions.size === 0
        ? 0
        : this.sum / this.transactions.size;
}
```

Расчёт среднего — **O(1)**, в отличие от полного `reduce()` по всем транзакциям при каждом обновлении. При вычислениях с денежными суммами в реальном продукте стоит использовать целочисленные минимальные единицы валюты или decimal-арифметику вместо неограниченного применения `Number`.

## 4. Скользящее окно: последние пять транзакций

При получении новой транзакции выполняется `update()`. Если размер `Map` превысил `LIMIT`, удаляется самый старый ключ:

```js
const LIMIT = 5;

const handlingData = (txUpdates) => {
    const store = storeRef.current;
    store.beginBatch();
    try {
        for (const tx of txUpdates) {
            store.update(tx);
            if (store.transactions.size > LIMIT) {
                const oldestId = store.transactions.keys().next().value;
                store.delete(oldestId);
            }
        }
    } finally {
        store.endBatch();
    }
};
```

`Map` сохраняет порядок **вставки**. Вызов `set()` для существующего ключа не переносит его в конец: обновление суммы не делает транзакцию «новейшей». Если окно должно сортироваться по `createdAt` или времени последнего изменения, это нужно реализовать отдельно.

## 5. `useSyncExternalStore`: подписка и снимок

Хук принимает:

```js
useSyncExternalStore(subscribe, getSnapshot, getServerSnapshot?);
```

- `subscribe(callback)` регистрирует обработчик изменения и **возвращает функцию отписки**.
- `getSnapshot()` возвращает текущее значение, на основании которого React решает, требуется ли рендер.
- `getServerSnapshot()` необходим при SSR и должен обеспечивать согласованный начальный снимок на сервере и при гидратации.

### Подписка таблицы только на ID

```jsx
const storeRef = useRef(null);
if (storeRef.current === null) {
    storeRef.current = new TransactionsStore();
}

const subscribe = useCallback(
    callback => storeRef.current.subscribeIdsList(callback),
    []
);
const getSnapshot = useCallback(
    () => storeRef.current.getIdsSnapshot(),
    []
);
const transactionIds = useSyncExternalStore(subscribe, getSnapshot);
```

Если список ID не изменился, `getIdsSnapshot()` должен вернуть **ту же ссылку на массив**. Нельзя делать `return [...this.transactions.keys()]` при каждом вызове: новый массив нарушает стабильность snapshot и вызывает лишние обновления (вплоть до цикла рендеров).

### Подписка строки по ID

```jsx
const TransactionRow = React.memo(function Row({ id, store }) {
    const subscribe = useCallback(
        callback => store.subscribe(id, callback),
        [id, store]
    );
    const getSnapshot = useCallback(
        () => store.get(id),
        [id, store]
    );
    const transaction = useSyncExternalStore(subscribe, getSnapshot);
    return <div><div>{id}</div><div>{transaction?.amount}</div></div>;
});
```

Это пример с **оригинальными названиями** методов из твоего кода. Изменённая транзакция должна сохраняться как **новый объект**, а неизменённые — сохранять прежние ссылки. Мутация объекта на месте не гарантирует обновление React, поскольку сравнение snapshots использует `Object.is`.

### Подписка среднего

`AverageAmount` использует отдельные `subscribeAverage()` и `getAverage()` через локальные `subscribe` и `getSnapshot`. При изменении суммы/количества транзакций Store уведомляет эту подписку, не затрагивая список ID, если состав окна прежний.

### Если используется SSR

Для всех вызовов `useSyncExternalStore` нужен корректный третий аргумент. Например, для **изначально пустого** Store можно определить **стабильный** пустой снимок:

```js
const EMPTY_IDS = [];
const getServerIdsSnapshot = () => EMPTY_IDS;
```

Нельзя передавать `() => []`, создающую новый массив при каждом вызове. При гидратации начальные данные должны совпадать с теми, которые сервер использовал для HTML. В нашем отдельном учебном React + Vite проекте без SSR третий аргумент не требуется.

## 6. `React.memo`, `useCallback`, `useMemo`, `useRef`

- **`React.memo(Row)`** позволяет пропустить рендер строки, когда её props не изменились. Компонент лучше объявлять вне `TransactionsTable`, чтобы тип компонента оставался стабильным.
- **`useCallback`** сохраняет идентичность функций `subscribe` и `getSnapshot` между рендерами при неизменных зависимостях; это предотвращает ненужные переподписки.
- **`useMemo`** кеширует результат вычисления или ссылку на объект, но **сам по себе не блокирует рендер дочернего компонента**.
- **`useRef`** хранит Store между рендерами, не инициируя рендер при изменении `.current`.
- **`key={id}`** сохраняет идентичность строки при изменении списка; индекс массива как ключ здесь нежелателен.

Антипаттерн:

```jsx
<Row transaction={{ ...item }} />
```

Создаёт новый объект на каждом рендере родителя и обнуляет выгоду от `React.memo` при сравнении props. Лучше передавать исходную стабильную ссылку или, как в нашей архитектуре, `id` и `store`.

## 7. Пакетирование уведомлений (`batching`)

`beginBatch()` включает накопление изменений. В текущем коде `update()` добавляет ID в `changedIds`, а `delete()` **не добавляет** удалённый ID в `changedIds`; обе операции устанавливают нужные флаги. Внутри batch уведомления не рассылаются.

`endBatch()`:

1. Уведомляет подписчиков ID из `changedIds`, затем очищает Set.
2. Вызывает `notifyAverage()`, если `averageChanged === true`.
3. Если `idsChanged === true`, один раз пересоздаёт `idsSnapshot` и вызывает `notifyIdsList()`.
4. Сбрасывает флаги. Уведомления основаны на флагах операций, **не на сравнении итогового значения**.

Преимущество: несколько операций не вызывают каскад повторных уведомлений. При этом **число вызовов подписчиков и число React commits — не одно и то же**: React может дополнительно объединять обновления.

Нюансы реализации: нужен корректный `try/finally`; вложенные batch требуют счётчика глубины либо явного запрета; для дальнейшей оптимизации можно сравнивать **итоговое состояние** с состоянием до batch. Сейчас временное добавление и удаление одного ID всё равно установит `idsChanged` и пересоздаст snapshot.

## 8. Ожидаемые рендеры

### Сценарий A: изменились суммы `tr_3` и `tr_4`

| Компонент | Ожидаемое количество рендеров |
| --- | ---: |
| `TransactionsTable` | 0 |
| `Row(tr_3)` | 1 |
| `Row(tr_4)` | 1 |
| Остальные `Row` | 0 |
| `AverageAmount` | 1, если среднее изменилось |

Почему: массив ID сохранил ссылку; подписчики `tr_3`/`tr_4` получили уведомления; подписчик среднего получил уведомление отдельно.

### Сценарий B: добавлена `tr_6`, удалена `tr_1` (LIMIT=5)

| Компонент | Ожидаемое поведение |
| --- | --- |
| `TransactionsTable` | 1 рендер из-за нового набора ID |
| `Row(tr_1)` | Размонтирование |
| `Row(tr_6)` | Монтирование |
| `Row(tr_2..tr_5)` | Без повторного рендера, если props/snapshots не изменились |
| `AverageAmount` | Рендер, если среднее изменилось |

## 9. Как проверить через React DevTools Profiler

1. Открой вкладку **Profiler** и нажми **Record**.
2. Выполни одно контролируемое обновление (например, только `tr_3` и `tr_4`).
3. Останови запись, выбери нужный **commit** и вкладку **Flamegraph**.
4. **Цветные** компоненты участвовали в рендере выбранного commit; **серые** — нет.
5. **Ranked** показывает участвовавшие компоненты по времени рендера.
6. В панели **What caused this update?** проверь инициаторов обновления.

В ходе упражнения Profiler показал: `TransactionsTable` серый, а обновление инициировали `Row(tr_3)`, `Row(tr_4)` и `AverageAmount`. Это подтвердило изоляцию подписок. На другом снимке при добавлении `tr_6` таблица и новая строка были цветными - также ожидаемо.

**Не путать:** Profiler группирует данные по commit; `console.count()` считает вызовы функции компонента. В development-режиме со `StrictMode` число вызовов может отличаться от числа завершённых commits.

## 10. Жизненный цикл и частые ошибки

**Render → Commit → Effects:** React сначала вычисляет дерево, затем применяет изменения к DOM, затем выполняет эффекты. `useEffect` не запускается при серверном рендеринге. Cleanup вызывается перед повторным запуском эффекта при изменении зависимостей и при размонтировании.

**Типичные ошибки:**

- Создавать Store в теле компонента без `useRef` → потеря состояния и подписок.
- Возвращать новый массив/объект из `getSnapshot()` на каждом вызове → лишние рендеры.
- Изменять транзакцию «на месте» → React может не увидеть изменение ссылки.
- Использовать `index` как `key` → неправильная идентичность строк при вытеснении старой транзакции.
- Передавать новый объект в `React.memo`-компонент при каждом рендере → `memo` не помогает.
- Забыть возвращать `unsubscribe` → утечки подписчиков.
- Читать устаревшее состояние из замыкания таймера с пустыми зависимостями (`[]`) → stale closure; используйте функциональное обновление состояния или подходящий `ref`.
- В SSR обращаться к `window` при импорте модуля → `window is not defined`; браузерный код запускать только на клиенте.
- В SSR не передать `getServerSnapshot` → `Missing getServerSnapshot`.

## 11. Сложность операций

| Операция | Типичная сложность |
| --- | --- |
| `Map.get/set/delete` | O(1) в среднем |
| Получение старейшего ключа `Map.keys().next()` | O(1) |
| Обновление `sum` и `getAverage()` | O(1) |
| Формирование нового массива ID | O(LIMIT) |
| Уведомление подписчиков | O(количество соответствующих подписчиков) |
| Рендер списка строк | O(LIMIT) при изменении списка ID; memo может пропустить рендер неизменённых строк |

При `LIMIT = 5` абсолютные затраты невелики. Ценность упражнения в масштабируемой модели **точечных подписок**, предсказуемом поведении и умении измерять обновления.

## 12. Итог

Разделены три независимые причины обновления UI: **данные конкретной транзакции**, **состав окна** и **среднее значение**. `useSyncExternalStore` связывает внешний Store с React; `React.memo`, стабильные props/snapshots и ключи предотвращают лишнюю работу; batching объединяет уведомления; Profiler позволяет проверить гипотезу на реальных commits.
